# Computer Graphics

#### 1. Rendering Pipeline
The rendering pipeline is a standardized data processing workflow that converts 3D scenes into 2D images. It consists of two main stages. The **Application Stage** runs on the CPU and handles scene management, occlusion culling, and submitting draw calls. The **Geometry Stage** runs on the GPU: the vertex shader performs coordinate transformations — converting to world space via the model matrix, to view space via the view matrix, and to clip space via the projection matrix. Then the primitive assembly stage assembles discrete vertices into continuous primitives, followed by clipping, perspective division, and viewport transformation to map to screen space. Next is the **Rasterization Stage**, which subdivides continuous primitives into fragments corresponding to screen pixels, performing perspective-correct interpolation of vertex attributes. The fragment shader then computes lighting, followed by the **Output Merging Stage** which sequentially executes Alpha Test, Stencil Test, Depth Test, and Alpha Blend to produce the final pixel color. If the hardware supports Early-Z, the depth test is moved before the fragment shader.

#### 2. Rendering Transparent Objects
First, render all opaque objects in the scene with both depth write and depth test enabled. Then disable depth write but keep depth test enabled. Sort all transparent objects strictly from back to front based on their distance from the camera. Finally, draw them sequentially using alpha blending to ensure correct occlusion and perspective relationships.

#### 3. Phong vs. Blinn-Phong
Both are classic empirical lighting models. The key difference lies in specular computation. The Phong model computes specular highlights using the cosine of the angle between the light's reflection vector and the view direction — when the angle is large, the highlight is harshly cut off and computing the reflection vector is relatively expensive. The Blinn-Phong model introduces the halfway vector (the angle bisector between the light direction and view direction) and computes the specular term as the dot product of the surface normal and the halfway vector. This is not only more efficient but also produces a smoother, more natural visual transition.

#### 4. Forward vs. Deferred Rendering
Forward rendering computes all affecting light sources for each object drawn. Its $O(\text{object count} \times \text{light count})$ complexity leads to substantial wasted lighting computation on occluded surfaces in multi-light scenes. Deferred rendering splits the process into two passes. First, a **Geometry Pass** writes the base attributes (normal, color, depth, etc.) of all visible objects into screen-space G-Buffers. Then a **Lighting Pass** computes lighting directly on these visible pixels, reducing complexity to $O(\text{object count} + \text{screen pixels} \times \text{light count})$. This eliminates the multi-light performance bottleneck, but at the cost of significant memory bandwidth and difficulty handling transparent objects.

#### 5. Normal Mapping — Transforming from Tangent Space to World Space
To allow a single normal map to be reused on model surfaces of different orientations, the normal data in the map is stored in local tangent space. At render time, we extract the vertex normal (N), the tangent aligned with the texture U direction (T), and the bitangent aligned with the V direction (B). Using these three vectors transformed to world space, we construct a $3 \times 3$ TBN matrix (by columns). In the fragment shader, the sampled tangent-space normal is multiplied by this TBN matrix to obtain the world-space normal used for environment lighting calculations.

#### 6. At Which Stage Do Alpha Test and Alpha Blend Occur?
Both Alpha Test and Alpha Blend occur in the final core stage of the rendering pipeline — **Output Merging (ROP, also called the per-fragment operation stage)**. Specifically, after the fragment shader computes the fragment's color and alpha value, the pipeline first executes **Alpha Test**, directly discarding fragments that fail the threshold condition to save computation overhead. Fragments that pass all tests (including depth and stencil) then undergo **Alpha Blend** when being written to the color buffer, where their color is blended with the existing background color according to a specified blend equation (e.g., based on the source and destination alpha ratio).

#### 7. Euler Angles vs. Quaternions
Two methods for representing rotation. Euler angles describe orientation through sequential rotation around three mutually perpendicular axes, but suffer from **gimbal lock** — when two rotation axes align, one degree of freedom is lost, so rotation angles are typically restricted. Quaternions avoid gimbal lock entirely.

#### 8. Early-Z and Z-Pre-Pass
**Early-Z** is a pipeline optimization automatically executed by GPU hardware. It moves the traditional depth test before the fragment shader to directly discard occluded fragments, provided the fragment shader does not modify depth or use `discard`. **Z-Pre-Pass** is a rendering strategy actively controlled by the developer. The scene is rendered twice: a first Pre-pass disables color writing, computes vertex positions, and outputs only the depth buffer; a second pass performs normal color rendering with the depth test set to "Equal" or "LEqual." Combined with Early-Z hardware, this ensures that even in complex scenes with interpenetrating polygons, each visible pixel on screen is computed by the fragment shader only once, saving performance.

#### 9. Multi-Light Optimization in Deferred Rendering
Treat each point light as a sphere. When a screen pixel falls within the projected coverage of this sphere, the GPU samples the G-Buffer at the screen coordinates to perform lighting calculations.
**TBDR (Tiled-Based Deferred Rendering)**: The screen is divided into tiles. In a Compute Shader, a frustum is constructed from each tile's min and max depth, and lights that actually intersect that tile spatially are identified. The intersecting light indices are stored in an SSBO. During the final lighting phase, for each pixel in the tile, the shader samples the G-Buffer once and then iterates over the intersecting light list for lighting computation.

#### 10. Shader Buffer Byte Alignment
To maximize throughput, the GPU memory controller typically reads VRAM in 16-byte units. In the `std140` layout, each data type has a fixed base alignment: scalars like `float` and `int` are 4 bytes, `vec2` is 8 bytes, `vec3` and `vec4` are both 16 bytes (vec3 is padded). A variable's starting memory offset within a struct must be a multiple of its base alignment. Additionally, `std140` mandates that each element in arrays and structs must have its base alignment rounded up to a multiple of 16 bytes.
The `std430` layout was introduced for SSBOs as a more compact memory layout. Its key breakthrough is removing `std140`'s forced 16-byte alignment for arrays and structs. `std430` is typically only used for read-write SSBOs, while UBOs generally still use `std140`.

#### 11. Perspective-Correct Interpolation
When the vertex shader outputs vertex attributes (texture coordinates UV, normals, vertex colors), the rasterization stage must compute, via interpolation, the attribute values corresponding to each pixel inside the triangle. However, simple linear interpolation in 2D screen space causes severe visual distortion under 3D perspective projection. Vertex attributes themselves cannot be linearly interpolated, but the reciprocal of vertex depth ($1/Z$) remains linear in screen space. Thus, for a pixel, first interpolate the depth reciprocal, then interpolate (attribute divided by depth), and divide the second result by the first to obtain the correct per-pixel attribute.
In shaders, variables passed from the vertex shader to the fragment shader undergo perspective-correct interpolation by default (hardware). To disable this, prepend the variable with the `noperspective` qualifier.

#### 12. SSAO
**Screen Space Ambient Occlusion** leverages the G-Buffers from deferred rendering to compute, in screen space, the degree to which a pixel's corresponding world-space point is occluded by surrounding geometry. First, the depth buffer is used to reconstruct the pixel's world-space point P. A hemisphere sampling kernel is constructed on the CPU. Using the normal data from the G-Buffer, the kernel is placed at the world-space point facing outward. To prevent banding artifacts, a random vector noise is used to rotate each pixel's sampling kernel. Each sample point is then reprojected back to screen space and compared against the current depth — if greater, the sample is occluded and the occlusion ratio increases. Finally, the resulting grayscale image is blurred.

#### 13. Shader Performance Optimization
1. Avoid branching where possible. `if-else` in GPU hardware executes both branches. Prefer math functions like `mix`, `step`, `smoothstep` instead.
2. Optimize mathematical computations: `sin()`, `cos()`, `pow()` are relatively expensive. For example, convert division to multiplication by reciprocal, and convert $x^{1.5}$ to $x \cdot \sqrt{x}$.
3. Reduce texture sampling.

#### 14. Order-Independent Transparency (OIT)
Traditional alpha blending requires strict back-to-front CPU-side sorting of all semi-transparent objects by camera distance before rendering. For interpenetrating geometry, precise per-object sorting is impossible, and for scenes with many transparent objects, sorting overhead becomes prohibitive. The core idea of OIT is to abandon sorting.
One approach is **Depth Peeling**: render the scene's semi-transparent geometry once with standard depth testing (recording the nearest fragment depth in the depth buffer), then perform multiple passes, each feeding the previous pass's depth buffer to the fragment shader. A fragment only participates in standard depth testing if its depth is greater than the previous pass's depth. Repeat until zero pixels are drawn, yielding multiple color buffers which are then blended from back to front.
Another OIT approach uses Compute Shaders and SSBOs. A large SSBO is allocated in VRAM. In the fragment shader, when a transparent pixel is rendered, atomic operations are used to insert the fragment's data (color, depth, alpha) into the SSBO. Each pixel has a linked list (stored in the SSBO) storing all such fragment data. After all transparent objects are rendered, a full-screen Compute Shader is launched. Each thread handles one screen pixel, traversing the pointer chain to retrieve all fragment data, sorts them by depth in registers, and performs standard alpha blending from back to front to produce the final color.

#### 15. Uniform vs. Texture vs. Buffer
1. **Uniform**: Read-only. Stored not in VRAM but in the GPU stream processor's internal registers, making reads extremely fast, but capacity is limited. Typically used for small, frequently-changing data like MVP matrices and time.
2. **Texture**: Has dedicated texture sampling units in the GPU, so reads are faster than buffers.
3. **Buffer**: Generally refers to UBOs and SSBOs — contiguous blocks of VRAM. Reading requires indexing. Can be read-write.

#### 16. How Is Tangent Space Defined?
Tangent space consists of three orthonormal basis vectors: the **Normal** (N) is perpendicular to the vertex's surface; the **Tangent** (T) is parallel to the surface, aligned with the texture U-axis growth direction; the **Bitangent** (B) is parallel to the surface, aligned with the V-axis growth direction, typically computed as $B = N \times T$.
In the rendering pipeline, after transforming the three vectors to the same coordinate space, they are arranged column-wise into a $3 \times 3$ TBN matrix:
$$
\begin{bmatrix}
T_x&B_x&N_x \\\\
T_y&B_y&N_y \\\\
T_z&B_z&N_z
\end{bmatrix}
$$
This matrix converts vectors from tangent space to the target space (e.g., world space). The tangent basis is initially defined in model space; multiplying the three vectors by the model matrix yields the world-space TBN matrix for transforming normals to world space.

#### 17. PBR Theory
1. **Microfacet Theory**: Assumes all surfaces are composed of countless tiny planar facets. Surface roughness determines the divergence of these micro-facet normals, which in turn determines the concentration of specular reflection.
2. **Energy Conservation**: The total energy of light leaving a surface cannot exceed the total energy of incoming light. Practically, the sum of diffuse and specular ratios must not exceed 1.
3. **Fresnel Effect**: A surface's reflectance increases with the grazing angle of the viewing direction. At a 90° grazing angle, all materials approach 100% reflectance.

#### 18. Cook-Torrance BRDF
The full BRDF equation:
$$ f_r = k_d f_{lambert} + k_s f_{cook-torrance}$$
Where $k_d$ is the proportion of incoming light that is refracted and eventually diffused, $k_s$ is the proportion specularly reflected, satisfying $k_d + k_s = 1$.

The Cook-Torrance specular term is the core of the model:
$$f_{cook-torrance} = \frac{DFG}{4(n \cdot \omega_o)(n \cdot \omega_i)}$$
It consists of three core functions (D, F, G) and a denominator:
1. **D — Normal Distribution Function**: Describes the alignment between micro-facet normals (halfway vector h) and the macro normal n. It determines the shape and size of the specular highlight. Trowbridge-Reitz GGX is commonly used.
2. **F — Fresnel Equation**: Describes the proportion of reflected light at different viewing angles. The higher the grazing angle, the higher the reflectance. The base reflectivity $F_0$ determines material properties. The Fresnel-Schlick approximation is common: $F = F_0 + (1 - F_0)(1 - \cos\theta)^5$.
3. **G — Geometry Function**: Describes the degree of micro-facet self-shadowing. When a surface is very rough, tiny protrusions occlude each other. Schlick-GGX or Smith's method is commonly used.
4. **Denominator**: A correction factor accounting for the difference between micro-facet projected area and macro-surface projected area.

The diffuse part uses the simplest Lambertian model:
$$f_{lambert} = \frac{c}{\pi}$$
Where $c$ is the surface base color. Dividing by $\pi$ ensures energy conservation when integrating over the hemisphere.

Coefficients: $k_s$ is directly equal to the Fresnel result, $k_d = 1 - k_s$. For pure metals, the diffuse ratio should be zero, so the metallic property in PBR materials requires special handling: $k_d = k_d \times (1.0 - metallic)$.

The final reflectance equation:
$$L_o(p,\omega_o) = \int_{\Omega}\left(k_d \frac{c}{\pi} + k_s \frac{DFG}{4(n\cdot\omega_o)(n\cdot\omega_i)}\right) L_i(p,\omega_i)(n\cdot\omega_i) d\omega_i$$

#### 19. PBR Material Maps
PBR materials typically include the following textures:
1. **Albedo**: Defines the surface base color. For non-metals, this is the diffuse color. For metals (which have no diffuse reflection), it actually represents the metal's base reflectivity $F_0$.
2. **Roughness**: Defines surface roughness, range 0–1. Directly affects the Normal Distribution Function D and Geometry Function G.
3. **Metallic**: Defines the surface metallicity, affecting the energy conservation mechanism and the Fresnel equation.
4. **Normal**: Defines the macro normal of the model surface.
5. **Ambient Occlusion**: Describes ambient light occlusion, reducing the intensity of diffuse ambient light.

#### 20. IBL (Image-Based Lighting)
IBL is the approach for handling indirect illumination and environment light in PBR rendering. Direct lighting (discussed above) only illuminates the side of an object facing the light source. The core idea of IBL is to treat an environment map as a massive light source where every pixel is a luminous point, abandoning real-time hemisphere integration in favor of a split-sum approximation with pre-computed lighting stored in textures.
1. **Diffuse Part**: A surface point receives diffuse light from all environment directions within its normal hemisphere. Offline tools traverse every direction in the cubemap and perform extensive sampling and integration (typically via convolution approximation) within the corresponding hemisphere, storing the result. In the shader, simply sample the cubemap with the normal and multiply by the base color to get the environment diffuse.
2. **Specular Part — Split-Sum Approximation**: The specular portion of the reflectance equation is split into two independent integrals.
    1. **Pre-Filtered Environment Map**: The first integral depends only on the environment map. Materials of different roughness reflect environment light at different clarity levels. The original HDR environment map is blurred at multiple levels and stored in the map's mipmap chain. In the shader, the reflection vector R is computed from the view direction V and normal N, and the corresponding mipmap level is sampled based on the current material roughness.
    2. **BRDF Integration LUT**: The second integral is independent of the environment map and depends on only two variables: roughness and the cosine of the angle between the normal and view direction. These two values serve as UV coordinates to sample a pre-computed lookup texture.

#### 21. OpenGL ES
OpenGL ES is essentially a stripped-down version of OpenGL for mobile.
1. **Tile-Based Rendering**: To save memory bandwidth, mobile GPUs do not draw directly to a full-screen framebuffer. Instead, they execute all vertex shaders first, then divide the screen into small tiles and execute subsequent pipeline stages per tile.
2. OpenGL ES requires explicit precision qualifiers for floating-point variables.
3. Texture compression formats differ.

#### 22. Vulkan vs. OpenGL
1. **Core Architecture**: OpenGL is a global state machine — commands like `glEnable` and `glBindTexture` modify the current global state. Vulkan abandons the global state machine design; all rendering state is pre-baked into Pipeline State Objects (PSOs).
2. **Memory Management**: OpenGL lets the driver manage VRAM — a call to `glBufferData` triggers automatic allocation. Vulkan requires manual memory allocation, manual memory fragmentation management, and manual binding of buffers and textures to specified memory offsets.

#### 23. Common Anti-Aliasing Techniques
1. **SSAA (Super-Sampling AA)**: Directly render at a higher resolution (e.g., 2×) then downsample to the target resolution. Cost: massive performance and VRAM overhead.
2. **MSAA (Multi-Sample AA)**: Uses multiple sample points per pixel. During rasterization, hardware determines coverage per sample point and records depth and stencil separately. Final color is blended based on the ratio of covered sample points. Pros: good performance. Cons: incompatible with deferred rendering pipelines.
3. **FXAA (Fast Approximate AA)**: A post-processing AA that uses edge detection algorithms to identify areas of high luminance/contrast variation and applies blur.
4. **TAA (Temporal AA)**: Injects a sub-pixel jitter into the projection matrix each frame, generates a velocity buffer recording each pixel's screen-space position change between the current and previous frame, then uses the motion vectors to back-project the current pixel to its position in the history frame, sampling and blending with a specific algorithm.

#### 24. Depth Test Settings for Opaque and Transparent Objects
1. Rendering opaque objects: depth test **on**, depth write **on**.
2. Rendering transparent objects: depth test **on**, depth write **off**.

#### 25. Typical Ray-Marching Volumetric Cloud Approach
1. Intersect the ray $r(t) = o + td$ from the camera with a bounding volume (e.g., a cube) defining the cloud layer, obtaining entry point $t_{in}$ and exit point $t_{out}$. Divide the effective distance within the cloud layer into $N$ discrete steps $\Delta S$.
2. In the shader, loop along the ray, advancing sample points $P_i = o + (t_{min} + i \cdot \Delta s)d$.
3. At each sample point $P_i$, sample a pre-generated 3D noise texture using its world coordinates as the density $\rho_i$.
4. Cast a secondary ray toward the light source and sample density from the sample point to the cloud boundary in the same way. Use the Beer-Lambert law to compute the attenuation coefficient of light reaching $P_i$, then use the phase function to compute the proportion of light undergoing single scattering into the camera's line of sight.
5. Compute the transmittance of the current sample point $T_i = e^{-\sigma \rho_i \Delta_s}$. Using the incoming light energy, local density, phase function, and step size, compute the current segment's color contribution and accumulate it into the total ray color, while updating the overall ray transmittance $T = T \cdot T_i$. Stop stepping when $T$ falls below a threshold (e.g., 0.01).

#### 26. SSGI (Screen-Space Global Illumination)
A screen-space GI solution built on deferred rendering.
1. In the fragment shader, reconstruct the 3D world-space position P of the current pixel from the depth buffer. Cast K random rays within the hemisphere around the surface normal N, stepping through 3D space at a fixed step size. At each step, reproject the sample point back to screen space and obtain its depth $Z_{ray}$ and the corresponding depth buffer value $Z_{buffer}$. When $Z_{ray} > Z_{buffer}$, the ray has entered the geometry represented by that screen pixel. Since the depth buffer records only one layer, a threshold $\Delta Z$ is introduced — when $Z_{ray} - Z_{buffer} < \Delta Z$, a physical intersection is confirmed.
2. Once intersection is confirmed, extract the color buffer value at the intersection point and compute the indirect lighting contribution to point P, incorporating distance attenuation and the cosine term. Due to the low number of rays per frame, the raw result is noisy and requires filtering/denoising.

#### 27. Common Occlusion Culling Techniques
1. **Precomputed Visibility Set (PVS)**: For static scene objects. During offline baking, the static scene is partitioned into a discrete spatial grid, computing which other cells are physically observable from each cell. This is stored as a static visibility connectivity graph. At runtime, the CPU directly looks up the table based on the camera's cell and only submits geometry from cells marked visible.
2. **Hardware Occlusion Queries**: A culling mechanism relying on CPU-GPU asynchronous communication. Two steps: first, the CPU submits the target object's bounding box as a test primitive to the GPU. The GPU rasterizes this bounding box against the current depth buffer (no color write, only recording the count of pixels passing the depth test). The CPU then reads back the query result — if the pixel count is zero, the object is occluded and its draw call is skipped.
3. **Hierarchical Z-Buffer Occlusion (HZB)**.

#### 28. Z-Fighting
Z-fighting occurs when multiple primitives have depth values that exceed the hardware's floating-point precision limits after perspective division, causing inconsistent visibility in depth testing. Due to the nonlinear mapping of the perspective projection matrix, depth buffer precision decays rapidly near the far clipping plane, making Z-fighting particularly severe in distant regions.
1. Push the near plane as far from the camera as feasible.
2. Use **Reverse-Z**: modify the projection matrix to map the near plane to $z = 1$ and the far plane to $z = 0$. Reverse-Z's numerical distribution counteracts the nonlinear precision decay introduced by perspective division.

#### 29. Shadow Map Self-Shadowing (Shadow Acne)
Self-shadowing in shadow maps arises from limited shadow map resolution — one texel corresponds to a finite area in 3D space. When rendering from the main camera's perspective, multiple fragments sample the same depth value from the shadow map, but their actual depths differ, causing incorrect occlusion.
**Depth bias** can be applied — forcing an offset onto the sampled depth during comparison — but this introduces **Peter Panning** (shadow detachment). Rendering the shadow map with front-face culling enabled (writing back-face depths) can mitigate this.

#### 30. Common Soft Shadow Techniques
1. **PCF (Percentage Closer Filtering)**: Rather than comparing depth against only a single shadow map texel, compare against multiple samples in a local neighborhood and average the results to obtain a soft shadow factor.
2. **PCSS (Percentage Closer Soft Shadows)**: Dynamically adjusts the PCF kernel size based on the relative distance between the occluder and the receiver.
3. **VSM (Variance Shadow Maps)**: Treats the shadow map as a statistical distribution. During shadow map generation, store not only depth but also depth squared in a separate texture. In the shading phase, the fragment shader samples both maps, computes variance, and uses Chebyshev's inequality to estimate the probability that the fragment depth exceeds the occluder depth, directly using it as the shadow factor.

#### 31. Ray Marching Optimization
1. **Adaptive Step Size**: Use spatial grid partitioning or similar methods to mark low-density regions in the volume, allowing larger step sizes through sparse areas.
2. **Early Termination**: Stop stepping when transmittance falls below a threshold (e.g., 0.01).
3. **Lower Resolution Rendering with Temporal Reuse**: Render the volume pass at a reduced resolution (e.g., quarter resolution), or use checkerboard rendering.

# C++

#### 1. `sizeof`
1. A C language operator that returns the memory size (in bytes) of a type or object.
2. Pointer size is always fixed: 4 bytes on 32-bit machines, 8 bytes on 64-bit.
3. When an array is passed as a function parameter, it decays to a pointer — `sizeof` returns the pointer size.
4. `sizeof` on a `char*` string includes the terminating `'\0'`; `strlen` does not.

#### 2. The `const` Keyword
1. Modifying a variable: indicates the variable cannot be modified.
2. Modifying a function parameter: indicates the parameter will not be changed inside the function.
3. Modifying a function return value: indicates the return value is read-only and can only be captured by a read-only variable.
4. Modifying a member function: indicates the function will not modify member variables. A `const` object can only call `const` member functions.

#### 3. The `static` Keyword
1. Modifying a global variable: limits the variable's scope to the current file. `static` global variables are initialized at program startup.
2. Modifying a local variable: the variable persists in memory across function calls rather than being destroyed on exit. Its value is preserved for the next call.
3. Modifying a function: limits the function's scope to the current file, preventing other files from accessing it and avoiding naming/redefinition conflicts.
4. Modifying member variables and member functions: indicates they are shared across all class instances and can be accessed directly through the class.

#### 4. The `extern` Keyword
1. Declares that a variable or function exists but does not define it — no storage is allocated. The compiler searches for the definition in other source files.
2. Passing global constants across files: `extern const int a;`. Global constants have internal linkage by default; to share across files, `extern` is required.
Role during compilation and linking:
3. At compile time, `extern` tells the compiler that a variable or function is defined elsewhere. The compiler creates a symbol table entry and establishes an unresolved reference to the symbol, which will be resolved during linking.
4. At link time, the linker locates the symbol definition in other object files and links them together.

#### 5. `extern "C"`
C++ uses name mangling to support polymorphism — function names are combined with parameter lists into an intermediate name during compilation. C does not do this, so linking can fail when C++ code tries to call C functions. `extern "C"` instructs the C++ compiler to use C linkage, enabling C++ code to call C functions or variables.

#### 6. The `volatile` Keyword
Modifying a variable indicates that it may be modified by external factors at any time. This prevents the compiler from optimizing accesses to the variable, ensuring every access reads from actual memory.

#### 7. The `explicit` Keyword
Modifies a function (typically a constructor declaration) to prevent implicit type conversions. When an argument is passed to a constructor, if the constructor is declared `explicit`, only explicit type conversion is allowed.
```
class MyInt{
public:
    MyInt(int n): num(n){};
private:
    int num;
};

void func(MyInt n){};
```
In the above, `func` can accept an `int` because the compiler implicitly converts `int` to `MyInt`. However, this can sometimes lead to unexpected behavior. Declaring the constructor as `explicit` forces `func` to only accept a `MyInt`.

#### 8. Byte Alignment
A memory allocation strategy. Without alignment, access efficiency may decrease. For example, on some platforms, every read begins from an even byte address — if data starts from an odd byte, two clock cycles are needed.
1. **Natural alignment**: For fundamental types, the natural alignment boundary is typically their size. `char` = 1 byte, `int`/`float` = 4 bytes.
2. **Struct alignment**: Each member is aligned to its natural boundary. The struct's total size is aligned to a multiple of the largest member's alignment.
3. **Union alignment**: Aligned to the largest member, since a union's members share memory.

#### 9. `class` vs. `struct`
1. `class` members are `private` by default; `struct` members are `public` by default.
2. `class` inheritance is `private` by default; `struct` inheritance is `public` by default.
3. `class` can be used as a template type parameter; `struct` cannot.

#### 10. `define` / `inline` / `typedef`
1. `define`: Simple text substitution. No type checking.
2. `inline`: Inline function. The compiler tries to replace calls with the function body to avoid call overhead. The function body is duplicated, consuming more code segment space.
3. `typedef`: Creates an alias for an existing type. Type checking is performed.

#### 11. Four Types of Casting
1. `static_cast`: Similar to C-style `()` casting. Used for fundamental type conversions (`int` to `long`) and pointer conversions (typically base-to-derived). No runtime type checking — the programmer must ensure safety.
2. `dynamic_cast`: Primarily for converting base class pointers to derived class pointers. Performs runtime type checking; returns `nullptr` on failure.
3. `const_cast`: Removes the `const` qualifier from an object. May cause undefined behavior.
4. `reinterpret_cast`: Bit-level reinterpretation from memory. No type checking whatsoever.

#### 12. How `dynamic_cast` Works Under the Hood
Depends on Run-Time Type Information (RTTI), so it only works when the base class has virtual functions.
1. Queries the object's vptr to access RTTI information.
2. Compares the target type with the actual runtime type. If they match or the target is a base class, the cast succeeds.
3. If the target is a derived class, checks the class hierarchy — if found, the cast succeeds.
4. On failure: returns `nullptr` for pointers; throws an exception for references.

#### 13. Polymorphism
Polymorphism means one interface with multiple implementations, divided into **static** and **dynamic** polymorphism. Static polymorphism is achieved through function overloading and generic templates — the specific function is determined at compile time via parameter or type deduction. Dynamic polymorphism means a base class interface is implemented differently by different derived classes, relying on virtual functions. When a base class pointer points to a derived class object and calls a virtual function, the specific derived class implementation is invoked.

#### 14. Virtual Function Table (vtable)
The vtable is the concrete implementation mechanism for virtual functions. Every polymorphic class has a vtable storing the addresses of its virtual functions. Every object of a polymorphic class has a vptr pointing to its class's vtable.
If a derived class overrides a base class virtual function, the derived class's vtable replaces the base class function address with the overridden one. Thus, when a virtual function is called through a base class pointer, the vtable lookup finds the overridden function, invoking the derived class's implementation.

#### 15. Class Initialization Order
1. If there is inheritance, base classes are initialized first in inheritance order. In the case of virtual inheritance, the virtual base is initialized first.
2. Member variable initialization order depends only on their declaration order in the class.
3. After base classes and member variables are initialized, the class's own constructor body executes.
4. Destruction order is the exact reverse of initialization order.

#### 16. Why Should Base Class Destructors Be Declared Virtual?
Destruction order is the reverse of initialization: the derived class destructor should run first, then the base class. If we destroy a derived class object through a base class pointer, and the base class destructor is not virtual, only the base class destructor runs — the derived class destructor never executes. Declaring the base class destructor as virtual enables dynamic dispatch via the vtable, ensuring the derived class destructor is called first, then the base class destructor is called along the inheritance chain.

#### 17. Virtual Inheritance
Virtual inheritance solves the **diamond problem** in multiple inheritance. When derived classes B and C both inherit from base class A, and D inherits from both B and C, non-virtual inheritance leaves two independent and potentially conflicting copies of A's data in D's memory layout. B and C should inherit from A using virtual inheritance to ensure only a single base class A sub-object exists in the most-derived class D.

#### 18. Deep Copy vs. Shallow Copy
**Shallow copy** performs a simple member-wise value copy. If an object contains pointer members, shallow copy only copies the stored memory address, causing two objects' pointer members to point to the same memory — leading to double-delete and other issues. **Deep copy** goes beyond simple value copying: for pointer members, it allocates new memory and copies the actual content pointed to by the original pointer.

#### 19. Pure Virtual Functions
A pure virtual function is declared but not implemented in the base class, and derived classes must implement it. Syntactically: `virtual ... = 0`. A class containing pure virtual functions is an abstract base class and cannot be instantiated.

#### 20. Can a Member Template Function Be Virtual?
**No**. The compiler must determine the number of virtual function pointers when constructing the vtable, but template functions are only instantiated when actually called with a concrete type. If template virtual functions were allowed, the compiler could not predict how many instantiations would be generated and thus could not determine the vtable size. C++ prohibits this at the language level.

#### 21. Can a Constructor Be Virtual?
**No**. Virtual function dispatch relies on the vptr in the object's memory, but the vptr is only initialized during constructor execution to point to the class's vtable. Before the constructor completes, the object has not yet established its polymorphic form.

#### 22. Can a Constructor Call a Virtual Function?
**Yes**, but polymorphism does not apply. Only the version of the virtual function within the currently-constructing class's scope is called. During base class construction, the derived class's members are not yet initialized, and the vptr points to the base class's vtable, so only the base class's virtual function implementation is called.

#### 23. Smart Pointers
1. `shared_ptr`: Uses reference counting to allow multiple pointers to share ownership of the same memory. Internally, a raw pointer and a reference count (stored on the heap). Copying a `shared_ptr` atomically increments the count; destruction atomically decrements. When the count reaches zero, the memory is freed.
2. `weak_ptr`: Solves the `shared_ptr` cyclic reference problem. It observes an object without incrementing the reference count.
3. `unique_ptr`: Exclusive-ownership smart pointer. Guarantees the pointed-to memory is owned by only one `unique_ptr` — ownership cannot be shared. Automatically frees memory when it goes out of scope.

#### 24. `malloc` / `free` vs. `new` / `delete`
`malloc` and `free` are C **functions** for dynamic memory allocation.
`new` and `delete` are C++ **operators** for dynamic memory allocation.
`malloc` only allocates memory — you must manually pass the size. It returns a `void*` that requires explicit casting. `new` automatically computes the required size and invokes the class constructor to initialize the object.
If memory allocated by `new` is freed with `free`, the destructor is never called, potentially causing memory leaks. Conversely, freeing `malloc`-allocated memory with `delete` triggers undefined behavior because `malloc` never called a constructor, yet `delete` tries to call the destructor.

#### 25. `delete` vs. `delete[]`
`delete` frees a single object allocated by `new`. `delete[]` is designed for arrays allocated by `new[]` — it reads the array length stored by the compiler just before the array's starting address, then calls the destructors in reverse order (last to first), and finally frees the entire memory block containing both the length record and the array.

#### 26. `vector` Expansion Mechanism
When `push_back` / `emplace_back` etc. cause `size > capacity`, `vector` expands. Internally, it allocates a larger contiguous memory block on the heap at a multiple of the current size (e.g., 2×), copies or moves existing elements to the new memory, then destroys the original objects and frees the old memory.

#### 27. `push_back` vs. `emplace_back`
`push_back` accepts an existing object (or a value implicitly convertible to the target type) and copies it to the container's end. `emplace_back` accepts constructor arguments and constructs the element in-place at the container's end, avoiding temporary object copies.

#### 28. `vector` Iterator Invalidation
Vector iterator invalidation occurs in two scenarios:
1. **Insertion** triggers expansion, causing memory reallocation — all existing iterators, pointers, and references are invalidated. Even without expansion, iterators from the insertion point to the end are invalidated because elements shift backward.
2. **Deletion** causes all elements after the erased element to shift forward — iterators from the deletion point to the end are invalidated. In practice, always capture the return value: `it = vec.erase(it)`.

#### 29. Is `shared_ptr` Thread-Safe?
**No**. While `shared_ptr` performs atomic operations on the reference count, the manipulation of the raw pointer and the reference count adjustment are not atomic with respect to each other, allowing potential multi-threading races.

#### 30. Rvalue References and Move Semantics
A C++11 feature, primarily addressing the excessive pointless deep copies when handling temporaries in traditional C++. An **rvalue** is a value whose address cannot be taken (e.g., a function return value). Before C++11, assigning a temporary rvalue to an object triggered a deep copy. For example, when accepting a function returning a `vector`, a new memory block was allocated, elements were copied over, and the original memory was freed.
With rvalue reference support, classes can implement **move constructors** and **move assignment operators** that directly seize ownership of the memory, avoiding deep copies. `std::move` casts an lvalue to an rvalue.

#### 31. C++ Memory Layout
1. **Code segment**: Stores compiled binary executable instructions. Read-only.
2. **Constant storage**: Read-only. Stores unmodifiable constants like string literals.
3. **Global/Static storage**: Allocated at compile time. Stores global variables and `static` variables.
4. **Stack**: Stores function local variables, parameters, and return addresses.
5. **Heap**: Used for dynamic memory allocation. Memory allocated via `malloc` or `new` resides here.

#### 32. What Happens If You `delete this` in a Destructor?
Infinite recursion leading to stack overflow and crash. `delete` internally performs two steps: first calls the object's destructor, then frees the heap memory. If the destructor calls `delete this`, it re-enters the destructor infinitely.

#### 33. How Large Is an Empty Class?
1 byte. Every object must have a unique memory address, so the compiler assigns a 1-byte placeholder to guarantee addressability.

#### 34. Where Is the vtable Stored?
In the read-only data segment (constant segment).

# Unreal Engine

#### 1. UE Gameplay Framework
Broadly, "gameplay" is bounded by engine source code — changes requiring engine source modifications are considered engine development, while game content built on top of the engine is gameplay. Narrowly defined, gameplay encompasses game state and rules, 3C (Character, Camera, Control), and UI.
1. **GameMode**: Game rules. Usually only exists on the server. Implemented as `AGameModeBase` (the base class of `AGameMode`). A project can have multiple GameModes for different play styles, but only one can be active at a time.
2. **GameState**: Game state. Manages all connected clients and tracks/replicates game-level properties. Unlike PlayerState (which records individual player attributes), GameState manages global game properties like elapsed time, neutral resource counts, etc.
3. **Camera**: Represents the player's viewpoint and how the player observes the world. It provides visibility/occlusion culling for the pipeline and handles post-processing effects after rendering.
4. **Character**: A character is a special, walkable Pawn.
5. **Controller**: `AController` inherits from `AActor`. By default, one Controller corresponds to one Pawn. The Controller receives notifications of events occurring on its possessed Pawn, allowing it to respond to events, intercept them, and override the Pawn's default behavior. Controllers come in two types: **PlayerController** (handles Camera management, Input response, UPlayer association, HUD display, level transitions, audio control) and **AIController** (no player input needed — adds Navigation, Behavior Trees, etc.).
6. **HUD and UI**: HUD can be understood as an in-world visualization of PlayerState (e.g., health bars above monsters or characters). UI is overlaid on top of the rendered scene, providing interactive information to the player. The key difference: HUD is generally non-interactive, while UI refers to menus and other interactive elements.

#### 2. UE UI Framework — Slate vs. UMG
**Slate** is UE's in-house, cross-platform, pure-C++ UI framework. It uses a declarative macro syntax for building UI trees. Slate widgets derive from `SWidget`, bypassing the heavy overhead of `UObject`.
**UMG** is a visual editor built on top of Slate. Every visual widget in UMG corresponds to a Slate widget at the lower level.

#### 3. Relationship Between `AActor` and `UObject`
`AActor` directly inherits from `UObject`. All Actors are UObjects, but only Actors can be placed or spawned in levels. Any class inheriting from `UObject` automatically gains the engine's GC, reflection system, and serialization. `AActor` additionally has world-space coordinates, a lifecycle, and a component container.

#### 4. UE Reflection System
Reflection is a program's ability to examine and manipulate its own structure at runtime. With reflection, a game engine can know at runtime what properties and functions a class has, dynamically read/modify those properties, call those functions, or dynamically instantiate objects.
**Why reflection is needed**: For example, in a game engine, selecting an object in the editor populates its property panel with editable parameters.
UE's reflection is implemented through compile-time code generation. Developers use specific macros (`UCLASS()`, `USTRUCT()`, etc.) to mark elements for reflection. During project compilation, the **Unreal Header Tool (UHT)** scans all header files containing reflection macros, auto-generates C++ code containing reflection metadata, and then the standard C++ compiler compiles both the original and generated code together, registering the reflection data in engine memory.
The generated auxiliary code essentially creates metadata for reflected elements. For member variables, it records the byte offset. For functions, each `UFUNCTION()` gets a generated **thunk** (wrapper) function that unpacks parameters and calls the programmer's actual logic. Generated code contains many static local variables and global functions; during engine initialization, these metadata objects are registered into a global dictionary.

#### 5. How Do Blueprints and C++ Interact?
Through the **reflection system** and the **Blueprint Virtual Machine**.
- **Shared variables**: Using `UPROPERTY(BlueprintReadWrite)`. When a Blueprint reads or modifies an exposed variable, the BP VM directly obtains the C++ object's memory base address, adds the byte offset, and performs direct memory read/write.
- **Blueprint calling C++**: Using `UFUNCTION(BlueprintCallable)`. When the BP VM executes a Blueprint node, runtime parameters are pushed onto the VM's parameter stack, then the UHT-generated thunk function is called to unpack parameters and execute the logic.
- **C++ calling Blueprint**: `UFUNCTION(BlueprintImplementableEvent)` marks the function as implemented in Blueprint (override in a BP subclass). `UFUNCTION(BlueprintNativeEvent)` provides a default C++ implementation that Blueprints can override — the C++ function must have the `_Implementation` suffix.

#### 6. Blueprint Virtual Machine
The BP VM is the underlying execution engine for Blueprints. Blueprints are fundamentally a stack-based VM language. During compilation, visual nodes are converted to an AST and ultimately to bytecode and reflection metadata. At runtime, the engine uses the `FFrame` struct as execution context, reads and parses bytecode opcodes sequentially, and calls `ProcessEvent` to execute the corresponding logic.

#### 7. UObject Lifecycle
A UObject's lifecycle begins with allocation from a memory pool via `NewObject`, followed by the native C++ constructor and property loading. During its active lifetime, the lifecycle is managed by the engine's strong-reference network — no manual C++ `delete` is needed. Once the object loses all valid references or is manually marked as pending destruction, the engine's GC system takes over, sequentially executing `BeginDestroy` and `FinishDestroy` for low-level resource cleanup, and finally calling the native destructor to free memory.

#### 8. UE Garbage Collection
UE's GC uses a **Mark-and-Sweep** algorithm. A set of non-collectible objects (GameInstance, World, etc.) form the **Root Set**. GC traverses from the Root Set through all `UPROPERTY()`-referenced objects. Every reachable object gets a "reachable" flag in its `EObjectFlags`. In the **sweep phase**, the engine iterates over the global array of all current UObjects. Objects without the reachable flag have `ConditionalBeginDestroy()` called, rendering them unusable, after which resources are cleaned up and destructors called to free memory.

# Design Patterns

#### 1. MVC (Model-View-Controller)
Decouples data/business logic from the UI presentation layer.
1. **Model**: Encapsulates all underlying data structures, state, and business logic. Provides state query and modification interfaces.
2. **View**: Responsible for UI display.
3. **Controller**: Captures user input events and calls the Model for logic processing.
User action → Controller → updates Model state. Model changes → Observer pattern notifies View → View retrieves latest data and updates itself.
**Drawbacks**: View and Model have a direct dependency; View must be updated when Model data changes. At scale, Controllers often accumulate routing, data format conversions, and exception handling, becoming hard to maintain.

#### 2. MVP (Model-View-Presenter)
Cuts the direct link between View and Model by introducing a Presenter.
1. **Model**: Same role as MVC — cares only about data.
2. **View**: Degraded to a passive component — no business logic. Only exposes interfaces for updating UI elements.
3. **Presenter**: Receives events from the View, calls the Model for processing. After the Model finishes, the Presenter internally handles data formatting and logic decisions, then calls View interfaces to drive UI updates.
View delegates interaction events to Presenter. Presenter manipulates Model, gets data, and actively calls View interfaces to push data back to the UI layer.
**Pros**: Isolates View and Model.
**Cons**: All UI changes must be explicitly invoked by the Presenter through interfaces, causing interface definition count and boilerplate to increase linearly with UI complexity.

#### 3. MVVM (Model-View-ViewModel)
Introduces data binding.
1. **Model**: Same role as MVC/MVP.
2. **View**: Defines UI layout structure and declaratively binds to ViewModel data.
3. **ViewModel**: An abstraction of the View's state. Transforms Model data into a View-friendly format and exposes properties and commands.
The core of MVVM is **data binding** — View control properties and ViewModel state properties are mutually bound. When ViewModel updates data, the framework automatically updates the View. When the user inputs data in the View, it auto-syncs back to ViewModel.
**Pros**: Eliminates Presenter manual UI update code.
**Cons**: Must depend on the engine's automated data binding system (reflection, observer patterns, etc.), incurring implicit CPU and memory overhead. Debugging is harder because UI update logic is encapsulated/automated.

#### 4. Singleton Pattern
A class with only one instance.
```
class SystemManager {
public:
    static SystemManager& GetInstance() {
        static SystemManager instance;
        return instance;
    }

    SystemManager(const SystemManager&) = delete;
    SystemManager& operator=(const SystemManager&) = delete;

private:
    SystemManager() {}
    ~SystemManager() {}
};
```

#### 5. Factory Pattern
Encapsulates the object instantiation process. Clients do not use `new` directly; instead, they obtain instances (based on a common interface or base class) by calling factory methods.

#### 6. Observer Pattern
Establishes a one-to-many dependency between objects. When one object's state changes, all dependent objects are automatically notified and updated. The subject internally maintains a collection of registered observer references. When the subject's state changes, it iterates the list, calling each observer's common interface (e.g., `update()`).

#### 7. Object Pool
The primary goal is avoiding frequent memory allocation/deallocation. The pool pre-allocates a block of memory. Instead of directly allocating heap memory, objects are retrieved from the pool and activated for game logic. When an object's lifecycle ends, it is returned to the pool rather than freed.
```
class SomeClass{
public:
    SomeClass() {}
    SomeClass(int x, int y): x(x), y(y) {}
    void Spawn(int x, int y) {
        this->x = x;
        this->y = y;
    }
    void Kill(){
        this->x = 0;
        this->y = 0;
    }
private:
    int x;
    int y;
};

class Pool{
public:
    Pool(int poolSize){
        poolMemory.resize(poolSize);
        for(auto& m : poolMemory){
            st.push(&m);
        }
    }

    SomeClass* Get(int x, int y){
        if(!st.empty()){
            auto mem = st.top();
            mem->Spawn(x, y);
            st.pop();
            return mem;
        }
        return nullptr;
    }

    void Return(SomeClass* mem){
        mem->Kill();
        st.push(mem);
    }
private:
    std::vector<SomeClass> poolMemory;
    std::stack<SomeClass*> st;
};
```

# Operating Systems

#### 1. Four Necessary Conditions for Deadlock
Mutual exclusion, Hold and wait, No preemption, Circular wait.

#### 2. Deadlock Prevention Methods
- Break the **hold and wait** condition: Require processes to request all needed resources at once before execution.
- Break the **circular wait** condition: Impose a total ordering on resource types (assigning increasing global IDs) and require that processes request resources in strictly increasing order.

#### 3. Inter-Process Communication (IPC)
1. **Shared Memory**: The OS maps the same physical memory region into the independent virtual address spaces of multiple processes. Each process can directly read/write the region via pointers.
2. **Message Queue**: A linked-list structure maintained by the OS kernel. Processes append formatted data blocks to the queue; receiving processes can selectively read messages by type identifier.
3. **Pipe**: A shared file connecting a reader process and a writer process. Byte-stream oriented, with blocking reads and writes by default.

#### 4. Process vs. Thread
A **process** is the fundamental unit of OS resource allocation. A **thread** is the fundamental unit of CPU scheduling and execution. Processes have independent address spaces; threads share the address space of their owning process.

#### 5. Virtual Memory
The OS divides the virtual address space into fixed-size blocks called **pages**, and physical memory into equally-sized blocks called **page frames**. Each process has a **page table** mapping virtual page numbers to physical page frame numbers. When the CPU accesses a virtual address, the hardware Memory Management Unit (MMU) translates it to a physical address. If a page table lookup reveals the page is not in physical memory (**page fault**), a page-fault interrupt is triggered, swapping the missing page from the disk's swap area into physical memory and updating the page table.

# Computer Networks

#### 1. HTTP GET vs. POST
**GET** semantics: Retrieves a specified resource. It is safe and idempotent — multiple identical GET requests do not change the server's resource state. GET appends parameters to the URL's query string.
**POST** semantics: Submits data to a specified resource for processing. It is **not** idempotent. POST encapsulates data in the HTTP message body.

#### 2. TCP vs. UDP
**TCP** is a connection-oriented transport mechanism providing reliable delivery. Communicating parties establish a connection via a **three-way handshake** and tear it down via a **four-way handshake** (wave).
**UDP** is a connectionless transport mechanism.

# Internship Experience

#### 1. What Did the Performance Optimization Work Involve?
UI stuttering was mainly caused by the main thread performing too many operations simultaneously. The engine's UI architecture was based on Flash, with overhead split into Flash animation loading costs and Lua-side logic costs.
- **For animation-heavy UIs**: Too many fragmented animations were used to create the overall animation effect, causing multiple loadings. Identified which animations could be batched and had artists combine them for a single load.
- **For tabbed/paginated UIs**: Each page was originally a separate prefab, with completely duplicated widgets even when two pages had identical controls. Modified the loading logic so tabs no longer switch entire pages — instead, widget content refreshes based on the selected tab, reducing redundant nodes.
- **For UIs with many controls** (e.g., a buff list requiring instantiation of many controls at startup): Adopted frame-split loading — limiting instantiation to a fixed number of nodes per frame. While this could cause visible refresh delays on low-frame-rate devices, it effectively eliminated the loading spike at startup.
- **For lists with reusable components** (e.g., a scroll list): The traditional approach instantiates all list entries upfront. If entries are nested with sub-controls, invisible entries continue to exist. With many nodes, instantiation cost is high. Instead, instantiated only empty entries and deferred control instantiation until the entry became visible.
- **For UIs requesting large data from the server**: Split the data-requesting process into a separate Manager. When the UI opened, it notified the Manager to request data rather than requesting during initialization. The page only rendered; when the Manager's request completed, it notified the page to update.

#### 2. Camera Logic Editor
A tool for designers. The camera sequence for a cutscene was essentially a Lua array of keyframe tables. The requirement was a free-look camera (mouse-controlled camera movement). Computed the mouse's screen-space delta each frame, adding X offset to yaw and Y offset to pitch to derive the new camera forward vector.

#### 3. NPC Dialogue Editor
Implemented a **timed-choice** feature. Some dialogue sequences required timed choices. The choice options were recorded in the designer's table with a time limit and a default option. When the dialogue opened, a timer was set, and a countdown animation played. If the timer expired, the corresponding interface was called to simulate the player selecting the default option. The feature was integrated into the designer's editor.

#### 4. How Do Lua and C++ Interact?
Through the **Lua stack** and the **Lua VM**. A stack space is maintained in memory, where each element can be a Lua value. Whether C++ passes data to Lua or vice versa, one side pushes data onto the stack and the other reads it.
- **C++ calling Lua**: When the engine needs to execute Lua logic, C++ pushes the Lua function name and parameter list onto the stack, then calls the Lua VM API to execute the script. The Lua VM pops parameters from the stack, executes the script logic, pushes the return value, and C++ reads it from the stack top and cleans up.
- **Lua calling C++**: C++ provides thin wrapper functions to Lua with a specific signature (parameter is only the Lua stack). When Lua script calls a C++ function, the Lua VM pushes arguments onto the stack and jumps to the C++ wrapper. Inside the wrapper, C++ reads parameters from the stack, calls the actual C++ logic, and pushes the result back.

#### 5. Overall UI Framework — Flash–Scaleform–Lua
**Flash**: Presentation layer. Artists handle UI layout, vector graphics, and timeline animation. Outputs SWF files containing vector data and ActionScript — essentially a Flash animation.
**Scaleform**: A rendering middleware. Reads SWF files, uses its built-in ActionScript VM to execute internal UI interaction scripts. During rendering, it tessellates Flash vector graphics in real-time into 2D triangle meshes and submits draw calls to the underlying graphics API.
**Lua**: Logic layer. Accepts data from C++, executes UI business logic, and calls Scaleform's API to drive the ActionScript VM.

#### 6. Lua GC
Uses a **Mark-and-Sweep** algorithm. Since Lua 5.1, a **tri-color marking** scheme is used. Objects in memory are classified into three color states during a GC cycle:
- **White**: Not yet visited by GC. All objects start white at cycle start. After marking, remaining white objects are deemed unreachable and collected.
- **Gray**: Visited by GC, but the objects it references internally have not yet been fully traversed. Such objects sit in a pending queue.
- **Black**: Visited by GC, and all objects it references have been fully traversed. Black objects are safely alive. The algorithm stipulates that black objects must not directly reference white objects.
The execution flow has two phases:
**Mark phase**: Traverse the root set, mark objects gray and enqueue. Dequeue gray objects, mark them black, and mark their referenced objects gray and enqueue. Loop until the gray queue is empty.
**Sweep phase**: Traverse all objects, reclaim memory of white objects, and reset surviving black objects to white for the next cycle.

# Miscellaneous

#### 1. Frame Synchronization vs. State Synchronization in Online Games
**Frame Sync** (Lockstep): The core logic is "server forwards input, clients compute independently." The server is merely a message relay, receiving all client inputs at a fixed tick rate and broadcasting them to all clients. Each client receives the same input sequence and runs identical local logic to compute the current game state. **Advantages**: Low server CPU and bandwidth cost — only transmits input commands, not complex entity state. **Challenge**: Clients own the game logic, making anti-cheat difficult.

**State Sync**: The core logic is "server computes, client renders." The server runs all core game logic. Clients send player input operations to the server. The server computes results and sends the latest game state to clients, which render and display based on the received state. **Advantages**: Security — the server authoritatively computes all state. **Cost**: Higher server CPU load and bandwidth overhead.
